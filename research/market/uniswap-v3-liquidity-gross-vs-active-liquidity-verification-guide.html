市场结构与流动性 / 毛额

流动性核验：四档毛额加总是 2800，池子正在用的是 1000

Uniswap V3 的 liquidity() 注释写明，它是当前在区间内、池子可用的流动性，和所有 tick 上的流动性总和没有关系。ticks() 返回的 liquidityGross 是把这一档当作下沿或上沿的仓位流动性合计。教学里两笔仓位在 tick 为 0 时铸入：一笔 1000，边界 0 和 120；一笔 400，边界 60 和 180。四档毛额是 1000、400、1000、400，加总 2800。池子 liquidity 只有 1000，因为第二笔的下沿还在当前 tick 右边。向上穿过 tick 60 之后变成 1400。当前 tick 停在 90 时，这一档没有被初始化，毛额是 0。数字是教学值，不是 2026 年 11 月 5 日某个池子的读数，也不构成投资建议。

核验清单

  • ✓读池子的 liquidity()，不要把各档 liquidityGross 加总当成它。教学铸入之后，毛额之和是 2800，池子正在用的是 1000。
  • ✓下沿的 liquidityNet 是正的，上沿是负的。从左向右穿过时加上这个净额。从右向左穿过时，取反只发生在当次局部变量上，不写回存储。
  • ✓铸入时只有当前 tick 落在区间内部，才立刻改池子 liquidity。tick 为 0 时，边界 60 和 180 的那一笔毛额已经写上，池子 liquidity 不加 400。
  • ✓当前 tick 停在 90 时，ticks(90) 的毛额是 0。向上穿过 60、还没穿过 120 时，池子 liquidity 是 1400。价格从 0 走到 59，流动性仍是 1000，价格比是 1.005917142554。

1. 毛额记的是引用了这一档的仓位，一笔记在两档上

IUniswapV3PoolState v1.0.0 把 ticks(tick) 的第一个返回值 liquidityGross 注释成：把这一档当作下沿或上沿来用的仓位流动性合计。它不是池子此刻能用来成交的数量。同一接口把 liquidity() 注释成：当前在区间内、池子可用的流动性，并且写明这个值和所有 tick 上的流动性总和没有关系。两条注释已经把后文的 2800 和 1000 拆开了。

Tick.update v1.0.0 对下沿和上沿各调用一次。upper 为 false 时，liquidityNet 加上 liquidityDelta；upper 为 true 时，liquidityNet 减去 liquidityDelta。liquidityGross 两次都用 LiquidityMath.addDelta，所以一笔 1000 的仓位会在两个边界上各留下毛额 1000。把这两档毛额相加得到 2000，仓位自己的流动性仍是 1000。相加多出来的那一份，是同一笔流动性被记了两次，不是池子又多了一笔。

这和仓位核验：仓位上的流动性，不等于代币余额不是同一问。那篇问的是一笔仓位的 liquidity 能不能被读成 token0 和 token1。本篇假定那笔流动性数字已经读对，接着问许多档上的毛额能不能被加总成池子正在用的 liquidity。

2. 教学两笔，在 tick 为 0 时铸入

数字取小，是为了把加减写清楚。池子用 v1.0.0 构造函数里的费率 3000，间距 60，所以边界必须落在 60 的倍数上。这一点档距核验：费率 3000 的间距是 60，最外一档也不是 -887272已经核过。本篇的四档是 0、60、120、180，都能被 60 整除。

仓位 A 的流动性是 1000，下沿 0，上沿 120。仓位 B 的流动性是 400，下沿 60，上沿 180。两笔都在 slot0.tick 等于 0 时铸入。Tick.update 写下的结果是：tick 0 的毛额 1000、净额 +1000；tick 60 的毛额 400、净额 +400；tick 120 的毛额 1000、净额 -1000；tick 180 的毛额 400、净额 -400。四档毛额相加是 2800。没有任何一档的毛额等于 2800，也没有任何一档的净额等于 2800。

间距 60 时，Tick.tickSpacingToMaxLiquidityPerTick 先把 MIN_TICK -887272 和 MAX_TICK 887272 收到间距上，得到 -887220 和 887220，档数 29575，单档毛额上限是 11505743598341114571880798222544994。教学用的 1000 和 400 都远低于这个上限，update 不会以 LO 回退。2800 对 1000 的差，不是撞上了单档上限。

3. 铸入当时，只有落在区间里的那一笔进入池子

UniswapV3Pool v1.0.0 的 _modifyPosition 用当前 tick 分三支。tick 小于下沿，只算 token0，不改池子的 liquidity。tick 小于上沿，走区间内部，这时才用 LiquidityMath.addDelta 把 liquidityDelta 加进池子的 liquidity。否则只算 token1。tick 正好等于下沿时，第一条不成立，走内部。tick 正好等于上沿时，走最后一支，池子 liquidity 不加。

铸入时 tick 是 0。仓位 A 满足 0 小于 120，而且 0 并不小于下沿 0，所以走内部，池子 liquidity 从 0 变成 1000。仓位 B 的下沿是 60，0 小于 60，走第一支，池子 liquidity 保持 1000。B 的毛额和净额已经写在 tick 60 和 tick 180 上，只是这笔流动性还没进入池子正在用的那个数。把四档毛额加总写成 2800，等于把还没生效的 400、以及每笔都被记了两次的边界，一起算进了当前深度。

净额在铸入时就已经写好，但铸入本身不调用 Tick.cross。区间内部那一支直接改池子 liquidity，不会再把下沿的净额加一次。若有人先按内部分支加了 1000，再把 tick 0 的净额 +1000 加一遍，A 会被记成 2000。合约没有这第二步。

4. 穿过时加上净额，向左走的取反不写回

Tick.cross 把这一档的 feeGrowthOutside 等外侧累计量用全局值减自身，然后返回存储里的 liquidityNet。它不改 liquidityNet 的符号。swap 在价格向左、也就是 zeroForOne 为真时，把这个返回值取反，取反的是当次的局部变量，随后用 LiquidityMath.addDelta 加进 state.liquidity。向右走时不取反。下一次反向穿过，读到的仍是原来的净额，再按方向决定要不要取反。把取反后的值写回 ticks(tick)，下一次穿过会多翻一次符号。

从 tick 0 向右。穿过 tick 60 时净额是 +400，不取反，池子 liquidity 从 1000 变成 1400。穿过 tick 120 时净额是 -1000，变成 400。穿过 tick 180 时净额是 -400，变成 0。四档毛额在这三次穿过里都不变，加总一直是 2800。池子正在用的数依次是 1000、1400、400、0。四个数里没有 2800。

已经到了 1400 再向左穿过 tick 60，zeroForOne 把 +400 取成 -400，池子 liquidity 回到 1000。存储里的净额仍是 +400。笔记若写「向左走过之后，tick 60 的净额变成了 -400」，下一次向右穿过会被算成再减 400，池子 liquidity 会少 800。

5. 当前 tick 可以没有毛额，价格先动、流动性后动

向上穿过 tick 60 之后，只要还没碰到 tick 120，池子 liquidity 保持 1400。tick 90 落在这段里。90 不是 60 的倍数，也不是任何一笔仓位的边界，ticks(90) 返回的是默认结构，毛额是 0，initialized 是 false。把这一档的毛额写成池子正在用的流动性，会得到 0。池子 liquidity() 仍是 1400。当前 tick 和某一档被初始化，是两件事。

价格可以先变，流动性稍后才变。沿用本站开方价那篇的截断，1.0001 的整数次方切到小数点后 12 位，不四舍五入。tick 0 到 tick 59 的价格比是 1.005917142554。这两档之间没有初始化的 tick，swap 不会调用 cross，池子 liquidity 仍是铸入后的 1000。tick 0 到 tick 60 的价格比是 1.006017734268，只比 59 档多出的那一档，才是净额 +400 被加进去的地方。把 1.005917142554 的价格移动写成「深度已经加上 400」，是把还没发生的穿过提前记了账。

再往外的两段价格比是：120 档为 1.012071681663，180 档为 1.018162060104。它们描述的是价格，不是流动性。穿过 tick 120 时流动性从 1400 降到 400，降的是净额的绝对值 1000，不是价格比 1.012071681663。把价格比和 liquidity 放进同一次加减，单位已经不同。

6. 先问读到的是毛额、净额，还是池子的 liquidity

错误句式是「把所有 tick 的 liquidityGross 加起来，就是池子的深度」，以及「当前 tick 的毛额就是正在用的流动性」。更可靠的句子是「liquidity() 的当前值；每一档的 liquidityGross 和 liquidityNet；铸入时 slot0.tick 落在区间内还是区间外；下一次穿过是向左还是向右；取反有没有被写回存储」。教学档里，毛额之和是 2800，铸入之后池子正在用的是 1000，穿过 tick 60 之后是 1400，穿过 tick 120 之后是 400，穿过 tick 180 之后是 0。tick 停在 90 时毛额是 0。tick 0 到 59 的价格比是 1.005917142554，这段价格移动不改变 1000。

本文是分析框架。liquidity() 与 ticks() 的注释来自 v1.0.0 的 IUniswapV3PoolState。毛额、净额和 cross 的返回值来自同一标签的 Tick。铸入时按当前 tick 分三支、以及 zeroForOne 时对净额取反，来自同一标签的 UniswapV3Pool。单档上限 11505743598341114571880798222544994 由 Tick.tickSpacingToMaxLiquidityPerTick 对间距 60 算出。1.005917142554、1.006017734268、1.012071681663 和 1.018162060104 是 1.0001 的整数次方截断到 12 位的教学值。这些数不是 2026 年 11 月 5 日某个池子的读数，也不构成投资建议。

7. 常见误读

四档 liquidityGross 加总是 2800，池子的 liquidity 是不是也是 2800？

不是。v1.0.0 的 liquidity() 注释写明，它是当前在区间内、池子可用的流动性，和所有 tick 上的流动性总和没有关系。教学里两笔仓位在 tick 为 0 时铸入，四档毛额 1000、400、1000、400 加总 2800，池子 liquidity 是 1000。

当前 tick 停在 90，读 ticks(90) 的毛额是不是池子正在用的流动性？

不是。90 不是任何一笔仓位的边界，这一档没有被初始化，毛额是 0。向上穿过 tick 60 且还没穿过 tick 120 时，池子 liquidity 是 1400。

价格从 tick 0 走到 tick 59，可用流动性会不会跟着变？

不会。这两档之间没有初始化的 tick，穿过不会发生。价格比按 1.0001 的 59 次方截断到 12 位是 1.005917142554，池子 liquidity 仍是 1000。可用流动性要等价格从左向右穿过 tick 60，才会加上净额 400，变成 1400。

推广信息：若要自己准备少量两种代币，以便对照池子的 liquidity() 和某一档 ticks() 的毛额，可自行查看 Allswap 兑换 的报价、费用与限额。该入口与 2800 和 1000 哪个才是正在用的流动性无关，也不代表对平台服务作保证。任何兑换须用于真实、合规的研究支出，勿用于违法用途。
