手续费核验：增长量记下 3000，poke 之前 tokensOwed 仍是 0

Uniswap V3 把手续费先写成每单位流动性的增长量，仓位上的 tokensOwed 要等 Position.update 才结清。教学里，已经分给流动性提供者的 token0 手续费是 3000，当时池子正在用的流动性是 1000000。feeGrowth 的增量是 3000 乘 2^128 再除以 1000000 的向下取整，等于 1020847100762815390390123822295304634。poke 之前，流动性 250000 和 750000 的两笔仓位，tokensOwed 都是 0。poke 之后分别是 749 和 2249，加总 2998。按份额直接乘 3000 会得到 750 和 2250。同样 250000 的流动性若落在当前 tick 外面，区间内增量是 0，poke 之后仍是 0。数字是教学值，不是 2026 年 11 月 6 日某个池子的读数，也不构成投资建议。

ipfsWeb · 发布于 2026-11-06 09:36:16 北京时间（UTC+08:00）

核验清单

  • ✓先问 Position.update 有没有跑过。增长量已经按 3000 写入时，poke 之前两笔 tokensOwed 都是 0。
  • ✓分母是池子正在用的流动性 1000000，不是单笔仓位。250000 的仓位 poke 之后是 749，不是 3000，也不是 750。
  • ✓750000 的仓位 poke 之后是 2249。两笔相加是 2998。按比例直接乘 3000，得到的是 750 和 2250。
  • ✓同样 250000 的流动性，下沿在 tick 120，当前 tick 是 0。区间内增量是 0，poke 之后 tokensOwed 仍是 0。

1. tokensOwed 是检查点，增长量在另一处累加

Position.sol v1.0.0 的 Info 把手续费拆成两类字段。feeGrowthInside0LastX128 和 feeGrowthInside1LastX128 的注释是：上一次更新流动性或应付手续费时，区间内每单位流动性的累计增长。tokensOwed0 和 tokensOwed1 的注释是：应付给仓位主人的 token0、token1 手续费。前一对是检查点，后一对是已经从检查点结出来的余额。手续费先进入池子的 feeGrowthGlobal，再由 Tick.getFeeGrowthInside 算成区间内部的增长，最后才在 Position.update 里变成 tokensOwed。

update 用当前的 feeGrowthInside 减去该仓位自己的 Last，乘以更新前的 liquidity，再除以 2^128。FullMath.mulDiv 向下取整。算完之后，Last 被改成刚刚用过的 inside。liquidityDelta 为 0 时，只要原流动性大于 0，这次调用仍会结清手续费；原流动性为 0 则以 NP 回退。所以一次不改变流动性的 update，也就是 poke，会改 tokensOwed。只读 tokensOwed、不调用 update，看到的是上次结清之后剩下的数。

这和手续费核验：池子上的费率，不等于流动性提供者留下的那一截不是同一问。那篇把整笔 3000 按协议分母拆成流动性提供者留下的 2250 或 2500。本篇从「已经决定写入增长量的那一截」接着算。教学里这一截取 3000，是为了把后面的取整写清楚，不是把上一篇的协议分成再算一遍。

2. 3000 先除以池子正在用的 1000000

UniswapV3Pool v1.0.0 在协议抽成之后，把留给流动性提供者的手续费写成增长量：fee 乘 2^128，再除以当时 state.liquidity，用 mulDiv 向下取整，加进 feeGrowthGlobal。分母是池子正在用的流动性，不是某一笔仓位的流动性，也不是各档 liquidityGross 的加总。毛额会把同一笔记到上下两个 tick 上，那是流动性核验：四档毛额加总是 2800，池子正在用的是 1000的问题。本篇的 1000000 就是这次增长使用的分母。

仓位 A 的流动性是 250000，边界是 tick -60 和 60。仓位 B 的流动性是 750000，边界是 tick -120 和 120。当前 tick 是 0，费率档的间距是 60，这些边界都能被 60 整除。0 大于等于下沿、并且小于上沿，两笔都在区间内，池子正在用的流动性是 1000000。写入增长量的 token0 手续费是 3000。增量等于 3000 乘 2^128 再除以 1000000 的向下取整，是 1020847100762815390390123822295304634。token1 这一侧没有这笔手续费，增长量保持 0。

若整池 1000000 都属于同一笔仓位，稍后 poke 得到的是这个增量乘 1000000 再除以 2^128 的向下取整，等于 2999。3000 少掉的 1，来自第一次除法，不是协议又抽了一笔，也不是还有第三笔仓位没被算进来。

3. 区间内已经有增量，仓位上的应付仍是 0

Tick.getFeeGrowthInside v1.0.0 用当前 tick 决定上下两侧怎么取。tick 大于等于下沿时，下方增长直接用下沿的 feeGrowthOutside；否则用全局增长减去这个 outside。tick 小于上沿时，上方增长直接用上沿的 outside；否则用全局增长减去上沿的 outside。区间内部等于全局减去下方、再减去上方。

铸入时全局增长还是 0。Tick.update 的注释写明，一个 tick 被初始化之前的增长，约定全部算在这个 tick 的下方。只有 tick 小于等于当前 tick 时，才会把当时的全局增长抄进 feeGrowthOutside。教学里的下沿 -120 和 -60 都小于等于 0，抄进去的是 0。上沿 60 和 120 大于 0，outside 保持 0。手续费写入之后，A 在 tick 0：0 大于等于 -60，下方是 0；0 小于 60，上方是 0。内部增量就是那一整个 1020847100762815390390123822295304634。B 同样满足 0 大于等于 -120 且 0 小于 120，内部增量相同。

这个内部增量是一次 view。它不写仓位。两笔仓位的 Last 仍是铸入时的 0，tokensOwed0 仍是 0，tokensOwed1 仍是 0。页面若把 tokensOwed 标成「未领取手续费」，这里会显示 0，而池子的增长量已经记下 3000。0 表示检查点还没动，不表示这笔手续费没有发生。

4. poke 之后是 749 和 2249，不是 750 和 2250

poke 是 liquidityDelta 为 0 的 Position.update。A 用更新前的流动性 250000：增量乘 250000 再除以 2^128，向下取整，得到 749。Last 改成当前内部增长，tokensOwed0 从 0 变成 749。B 用 750000，得到 2249。两笔相加是 2998。token1 的差是 0，所以 tokensOwed1 不加。

不走定点、直接按份额乘：250000/1000000 乘 3000 是 750，750000/1000000 乘 3000 是 2250。合约每一笔都少 1。少掉的不是协议费。增长量在写入时已经向下取整一次；整池一笔仓位只能拿回 2999。再拆成两笔，每笔各自向下取整，2999 又少 1，变成 2998。把 749 和 2249 加回 2、凑成 3000，修的是展示，不是合约里能够结清的数。

update 用的是更新前的流动性。已经发生的增长，不会被这次新加进来的流动性追溯。一笔在手续费写入之后才铸入的仓位，旧流动性是 0，乘出来的应付是 0，Last 却会被推进到当时的内部增长。此后它只参与 Last 之后的新增长。用「现在的流动性份额乘历史总手续费」去补这 3000，把后来者写成了已经分掉的手续费的收款人。

5. 同样 250000，落在区间外就是 0

仓位 C 的流动性也是 250000，边界是 tick 120 和 180，在手续费写入前铸入，当前 tick 仍是 0。下沿 120 大于 0，初始化时不把全局增长抄进 outside，两侧 outside 都是 0。手续费写入后，0 小于 120，下方增长等于全局增量减去 0。0 小于 180，上方增长是 0。内部增量等于全局减去全局，结果是 0。poke 用 250000 去乘 0，tokensOwed 仍是 0。

A 和 C 的流动性同为 250000，也都在这笔 3000 写入之前已经存在。差别只在 tick 0 是否落在区间内。A 结出 749，C 结出 0。把 C 的 250000 除以池子的 1000000 再乘 3000，会写出 750。区间内部的增量里没有这 750。getFeeGrowthInside 对上沿用的是严格小于：tick 正好等于上沿时走外侧公式，和铸入时 tick 等于上沿不算在区间内是同一条边界。本篇的手续费发生在 tick 0，没有把价格推到上沿。

6. collect 花的是检查点，不重新计算增长

核心池的 collect 读取 tokensOwed，按请求额和余额中较小的一笔转出，再从 tokensOwed 里扣掉。它不调用 Position.update。poke 之前对 A 调用 collect，转出 0，Last 仍是 0，内部增量还在。下一次 poke 仍然算出 749。collect 没有把增长量消耗掉。

poke 之后 A 的 tokensOwed0 是 749。collect 转出 749，余额回到 0。再 collect 一次，转出 0。再 poke 一次也加不出新的应付，因为 Last 已经等于当前内部增长。只有新的手续费把内部增长推到 Last 前面，下一次 update 才会再结出非零的差。错误句式是「tokensOwed 就是这个仓位赚到的手续费」。更可靠的句子要写出：写入增长量的数额、做分母的在用流动性、这次增长之后 update 有没有跑过、仓位自己的流动性、当前 tick 在不在区间内。教学档里写入的是 3000。poke 之前两笔都是 0。poke 之后是 749 和 2249，加总 2998。区间外的那笔 250000 仍是 0。

本文是分析框架。检查点、乘积取整和 liquidityDelta 为 0 仍会结清，来自 Position v1.0.0。区间内增长的分支，以及初始化时把已有增长记到 tick 下方，来自 Tick v1.0.0。增长量用手续费乘 2^128 再除以当时流动性，以及 collect 只扣 tokensOwed，来自 UniswapV3Pool v1.0.0。1020847100762815390390123822295304634、2999、749、2249 和 2998 是这些整数除法的教学结果，不是 2026 年 11 月 6 日某个池子的读数，也不构成投资建议。

7. 常见误读

feeGrowth 记下 3000，tokensOwed 是不是也是 3000？

不是。3000 先按池子流动性 1000000 做成 feeGrowth 的定点增量。tokensOwed 要等 Position.update 用上次检查点做差，再按该仓位自己的流动性向下取整。poke 之前两笔都是 0。poke 之后是 749 和 2249，加总 2998。

按 25% 和 75% 去乘 3000，是不是得到 750 和 2250？

按流动性比例直接乘，250000/1000000 乘 3000 是 750，750000/1000000 乘 3000 是 2250。合约先把 3000 乘 2^128 再除以 1000000 向下取整，poke 时再乘仓位流动性除以 2^128。结果是 749 和 2249。

同样 250000 的流动性，区间在当前 tick 外面，poke 之后是不是也有 749？

不是。tick 0 落在下沿 120 左边时，getFeeGrowthInside 把这段增长算到区间下方，区间内部增量是 0。poke 之后 tokensOwed 仍是 0。

推广信息：若要自己准备少量两种代币，以便对照仓位的 tokensOwed 和池子的 feeGrowthGlobal，可自行查看 Allswap 兑换 的报价、费用与限额。该入口与 749 和 2249 哪个才是这次 poke 记下的应付手续费无关，也不代表对平台服务作保证。任何兑换须用于真实、合规的研究支出，勿用于违法用途。
