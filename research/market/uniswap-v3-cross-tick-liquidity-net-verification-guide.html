穿档核验：向左穿过 200 减去负 1000，流动性回到 5000

Uniswap V3 在穿过已初始化 tick 时，向右移动加上 liquidityNet，向左移动减去 liquidityNet。区间 [100, 200] 注入流动性 1000 时，下界 100 的 net 为 +1000，上界 200 的 net 为 -1000。当前活跃流动性 5000 向上涨破 200 时，5000 加上 -1000 变为 4000；当价格向左跌回重新穿过 200 时，4000 减去 -1000 回升到 5000。若向左跌破时漏掉取反符号误用加号，流动性会被错算成 3000，少算整整 2000 活跃深度，导致后续价格变化量与滑点预估严重失真。这些是 UniswapV3Pool 与 LiquidityMath 的整数规则，不构成投资建议。

核验清单

  • ✓ticks[tick].liquidityNet 记录的是价格由低向高跨过该 tick 时的净变动。头寸下界为正，上界为负。
  • ✓向右跨步（zeroForOne 为假，价格上涨）直接加上 liquidityNet：5000 加上 -1000 等于 4000。
  • ✓向左跨步（zeroForOne 为真，价格下跌）必须执行取反（减去 liquidityNet）：4000 减去 -1000 恢复为 5000。
  • ✓向左跌破上界时若同向相加，流动性落到 3000，产生 2000 的双倍偏差；继续向左跌破下界 100 时，减去 +1000 使流动性回到 4000。

1. liquidityNet 的正负号按向上穿过定义

在 Uniswap V3 中，流动性头寸被限定在离散的价格区间 [tickLower, tickUpper] 之内。在合约内部的 Tick.update 函数中，流动性增量 liquidityDelta 对上下两个边界 tick 的处理有着严格的符号分工：

// Tick.sol
liquidityNet = upper
    ? int128(int256(liquidityNet).sub(liquidityDelta))
    : int128(int256(liquidityNet).add(liquidityDelta));

这意味着，当一个流动性提供者向区间 [100, 200] 注入 1000 单位流动性时，下界 100 的 liquidityNet 增加 1000（即 +1000），而上界 200 的 liquidityNet 则减少 1000（即 -1000）。这一约定的物理意义是：假定价格从负无穷向正无穷单向增长，当价格从左向右穿越 tickLower = 100 时，该头寸被激活，池子的活跃流动性增加 1000；而当价格继续向右穿越 tickUpper = 200 时，价格脱离了该头寸的提供范围，池子的活跃流动性必须扣除这 1000。

很多初次阅读合约的研究者容易产生误解，认为只要头寸是注入流动性，两个 tick 上记录的就都是正数。事实上，liquidityGross 记录的才是绝对值总和（两个 tick 上都是 +1000），而 liquidityNet 记录的是方向导数。只有明确了这个符号方向，才能进入下一步的穿档计算。

2. 向右穿过 200：5000 加上 -1000 变成 4000

当池子发生兑换时，如果输入的是 token1 换取 token0（zeroForOne = false），池子中的 token1 增加、token0 减少，边际价格上涨，当前 tick 向右移动。在 UniswapV3Pool.sol 的兑换主循环中，当某一步计算的目标价格打到了下一个已初始化 tick 时，池子执行穿档逻辑：

// UniswapV3Pool.sol
if (state.tick == step.tickNext) {
    int128 liquidityNet = ticks.cross(step.tickNext, ...);
    if (zeroForOne) liquidityNet = -liquidityNet;
    state.liquidity = LiquidityMath.addDelta(state.liquidity, liquidityNet);
}

假设在跨过 200 之前，当前池子的全局活跃流动性 state.liquidity 为 5000。由于 zeroForOne 为假，合约不会进入 liquidityNet = -liquidityNet 的分支，保持原有的 liquidityNet = -1000 不变。

接着，LiquidityMath.addDelta(5000, -1000) 被执行。5000 加上 -1000 等于 4000。池子的当前活跃流动性从 5000 下调为 4000。这个整数变动完全符合直觉：价格涨出了 [100, 200] 区间，该区间的 1000 流动性全部变成了 token0 被兑换者提走，不再参与高于 200 的后续价格波动，因此全局流动性只剩下 4000。

3. 向左跌回穿过 200：减去 -1000 回到 5000

现在观察相反的行情。假定价格曾经上涨到 250，此时池子活跃流动性维持在 4000。随后市场发生大额抛售，兑换者使用 token0 换取 token1（zeroForOne = true），价格向下暴跌，当前 tick 从 250 向左移动，重新穿过 200。

在向左跨越 tickUpper = 200 时，ticks.cross 读取出来的 liquidityNet 依然是该 tick 静态存储的 -1000。但是，因为 zeroForOne 为真，合约执行了关键的反转操作：

if (zeroForOne) liquidityNet = -liquidityNet;

此时，-1000 被取反为 -(-1000) = +1000。随后调用 LiquidityMath.addDelta(4000, 1000)，计算结果为 5000。活跃流动性从 4000 准确无误地回升到了 5000。

跨步场景当前流动性tick 位置静态 liquidityNetzeroForOne 方向生效变动量更新后流动性
向右进入下界4000tickLower = 100+1000false (涨)+10005000
向右离开上界5000tickUpper = 200-1000false (涨)-10004000
向左重新跌回上界4000tickUpper = 200-1000true (跌)+10005000
向左跌破离开下界5000tickLower = 100+1000true (跌)-10004000

表中第三行正是所有量化回测与链下路由模拟最容易出错的地方。许多非官方实现的聚合器或模拟脚本由于图省事，写成了 state.liquidity += tick.liquidityNet，在向左跌破上界时把 -1000 直接加到 4000 上，得到了荒谬的 3000。

4. 漏掉反转符号产生 2000 偏差的连锁反应

把向左跌回 200 算成 3000，表面上看起来只是少算了 2000 的数字，但对接下来的链上撮合与价格推导会产生灾难性的扭曲。

在穿过 200 之后，兑换尚未结束，循环继续调用 SwapMath.computeSwapStep。在这个函数中，给定剩余输入代币计算价格变化量时，分母正是刚才更新后的 state.liquidity：

ΔsqrtPrice = Δy / L

真实情况下，分母应该是 5000。如果错误算法将分母写成 3000，算出的价格变动幅度就被夸大了整整 5000 / 3000 ≈ 1.67 倍（放大了 66.7%）。这意味着：

  1. 离线套利机器人会以为池子已经没有足够深度，在极小的交易量下就会击穿滑点保护，从而主动放弃一笔本可盈利的无风险套利；
  2. 借贷清算引擎如果基于此模拟滑点，会高估抛售对现货价格的打压力度，错误给出提前折价清算的危险信号；
  3. 当价格继续向下穿过其它多个紧邻 tick 时，符号错误会持续正负倒置累加，最终使 state.liquidity 甚至变成负数或直接下溢回退，导致模拟交易进程崩溃。

5. 跌破下界 100：减去 +1000 变为 4000

继续沿刚才的下跌路径复算。当价格在 [100, 200] 区间内继续跌破 100 时，step.tickNext 抵达 tickLower = 100。该 tick 记录的静态 liquidityNet 是 +1000。

此时依然是下跌行情，zeroForOne 为真，合约执行取反：+1000 变成 -1000。全局流动性由 5000 加上 -1000，降回 4000。跌破下界之后，该区间的所有流动性全部转化为 token1，池子再次失去了这 1000 的活跃支持，活跃度降为 4000。整个下跌过程从 4000 恢复为 5000，再从 5000 退出为 4000，完美闭环。

核对一笔穿档兑换时，必须按以下步骤复查：首先确认 zeroForOne 的布尔值；其次读取触发跨步的 step.tickNext 的静态 liquidityNet；若 zeroForOne 为真，将 liquidityNet 乘以 -1；最后将其加到前序 liquidity 上。向左穿过上界 200 时，必须恢复为 5000，而不是跌落至 3000。

本文是分析框架。tick 存储的净变动量规则来自 Tick.sol，跨步取反与状态更新来自 UniswapV3Pool.sol 与 LiquidityMath.sol v1.0.0。4000、5000、3000 与 2000 的差额是这些整数运算的精确结果，不构成投资建议。

6. 常见误读

穿过已初始化的 tick，当前池子的活跃流动性是不是一定会变大？

不会。已初始化 tick 的 liquidityNet 可以是正数也可以是负数。当价格向上穿过头寸的上界 tick 时，liquidityNet 是负数，活跃流动性会减小；当价格向下穿过头寸的下界 tick 时，取反后同样让活跃流动性减小。只有在进入区间（向上穿过下界，或向下穿过上界）时，活跃流动性才会变大。

上界 200 的 liquidityNet 既然是负数，为什么 liquidityGross 还是正数？

因为两者统计的维度不同。liquidityGross 统计的是引用该 tick 作为边界的所有头寸流动性绝对值总和，始终大于等于 0，用于判断该 tick 是否仍在使用以及能否从 bitmap 中清理。liquidityNet 记录的是方向性净增减量，上界天然为负，表示价格继续向上时需要移除该头寸。

向左跌回穿过 200 时，如果代码忘记取反会发生什么？

会产生双倍偏差。以 4000 的活跃流动性为例，上界 net 为 -1000。正确计算是 4000 减去 -1000 得到 5000；若同向相加，会算成 4000 加 -1000 等于 3000。少算了 2000 的活跃流动性。在后续的兑换步进中，过小的流动性会导致价格下跌幅度被过度放大，引发严重的回测和报价偏差。

推广信息：精确核验穿档流动性是构建量化模型与离线路由的必要基础，而日常兑换往往通过路由聚合器屏蔽了底层的 tick 跨步细节。若在研究之余需要测试小额跨链兑换或现货交易体验，可自行查看 Allswap 兑换。该服务入口与 5000 还是 3000 的合约核验无关，亦不构成对任何第三方服务的保证。请合规使用链上工具，勿用于非法用途。
