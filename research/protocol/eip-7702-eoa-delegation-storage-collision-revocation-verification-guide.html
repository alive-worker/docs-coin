EIP-7702 委托账户核验：EOA 存储槽位碰撞、跨链重放与撤销残留陷阱

以太坊 Pectra 升级激活的 EIP-7702 彻底打破了“外部账户（EOA）不能执行合约代码”的十年铁律：用户只需签署一条 SetCode（Type 0x04）授权元组，即可将 23 字节委托指示符 0xef0100 || address 写入 EOA 代码区，原地址瞬间获得批量交易、Gas 代付与会话密钥能力。然而，这种“就地升级”在工程实践中暴露出三类高度隐蔽的资产安全陷阱：撤销或切换委托合约时 EOA 持久存储永不自动清空导致的槽位碰撞、chain_id = 0 签名引发的全链重放与目标地址抢注，以及全网存量 DeFi 合约赖以生存的 tx.origin == msg.sender 防线瞬间崩塌。

ipfsWeb · 加密货币研究编辑部 · 发布于 2026-11-25 09:58:51

核验清单：EIP-7702 委托账户四大边界检查

  • ✓ 代码指针与撤销残留核验：用 eth_getCode 核查地址是否以 0xef0100 开头（总长 23 字节）；切换或撤销委托后，必须单独用 eth_getStorageAt 排查旧槽位残留，切勿误以为归零代码即清空状态。
  • ✓ ERC-7201 命名空间隔离：核验目标委托实现合约是否禁止线性 Slot 0 排布，强制使用 ERC-7201 哈希命名空间存储，避免不同钱包实现间出现 owner/nonce 槽位互踩。
  • ✓ 签名元组 chain_id 与初始化鉴权：严禁签署 chain_id == 0 的跨链通配授权；核验实现合约的 initialize() 是否强制校验 msg.sender == address(this) 或 EOA 签名，杜绝同块抢跑接管。
  • ✓ 协议侧 tx.origin 假设退场：审计交互的 DeFi 协议是否仍依赖 tx.origin == msg.sender 或 extcodesize == 0 作为防闪电贷/防重入约束，此类约束在 EIP-7702 下已完全失效。

1. EIP-7702 底层状态机：23 字节 0xef0100 指针与存储归属

要看清 EIP-7702 的风险边界，必须从字节码级理解其与传统 ERC-4337 智能合约钱包的本质差异。ERC-4337 需要部署一个全新的代理地址并把资产迁移进去，而 EIP-7702 引入了全新的交易类型 0x04（SetCode Transaction），其携带的 authorization_list 包含若干由 EOA 私钥签署的授权元组：

// EIP-7702 授权签名哈希构造（MAGIC = 0x05）
authHash = keccak256(0x05 || rlp([chain_id, address, nonce]))

当打包者（Relayer 或用户本人）将该交易送上链并通过 ecrecover 验证签名后，EVM 会在该 EOA 账户的 code 字段写入一段固定 23 字节的委托指示符（Delegation Designator）：前 3 字节为 EIP-3541 保留字节 0xef0100（普通合约永远无法通过正常部署拥有 0xef 开头字节码），后 20 字节为目标实现合约地址。

关键的状态机后果在于：此后任何发往该 EOA 的调用，EVM 都会解析 0xef0100 后的地址并加载目标合约代码，但在该 EOA 自身的上下文中执行——就像 EOA 对目标合约执行了一次透明的 DELEGATECALL。这意味着目标合约里所有 SSTORE 写入的数据，全部持久化落盘在该 EOA 自己的 Storage Trie 中，而不是实现合约里。

2. 致命陷阱一：切换钱包与撤销委托不清空存储导致的槽位碰撞

许多用户与钱包前端存在一个极其危险的误区：认为只要发起一笔指向零地址 0x0000000000000000000000000000000000000000 的 EIP-7702 授权，把账户“还原为普通 EOA”，或者将委托从钱包 A 切换到钱包 B，原先的合约状态就会随之重置。这在 EVM 底层规范中完全不成立。

EIP-7702 的撤销操作仅将 EOA 的账户代码清空（codeHash 恢复为空字节哈希），绝不会遍历或清除 EOA 的任何 Storage 槽位。设想如下真实攻防路径：

  1. 用户此前将 EOA 委托给实现合约 WalletImplA，其线性布局将 Slot 0 用作自定义 uint256 public sessionNonce 或某个第三方中继器的白名单地址，执行过几次操作后 Slot 0 存有非零值；
  2. 随后用户撤销 WalletImplA，或直接重签授权将 EOA 切换至 WalletImplB，而 WalletImplB 的线性布局恰恰将 Slot 0 定义为 address public admin 或 bool public initialized；
  3. 切换完成的瞬间，WalletImplB 读取 Slot 0 会直接把旧合约遗留的脏数据解释为合法管理员地址或“已完成初始化”标志，轻则导致账户永久无法初始化（自锁），重则让旧地址直接获得 WalletImplB 的最高控制权，无需私钥即可转走资产。

工业级解决标准是强制要求所有 EIP-7702 委托实现合约放弃默认的线性槽位分配，严格遵循 ERC-7201（Namespaced Storage Layout），将每套实现的状态映射到由唯一字符串派生的伪随机槽位：

// ERC-7201 命名空间槽位计算公式（彻底隔离不同委托实现的存储）
// keccak256(abi.encode(uint256(keccak256("mywallet.v1.storage")) - 1)) & ~bytes32(uint256(0xff))
bytes32 private constant STORAGE_LOCATION =
    0x4a8f12c9b3d07e1f8c2a6b4d9e0f1a2b3c4d5e6f708192a3b4c5d6e7f8091000;

struct WalletStorage {
    address guardian;
    uint256 nonce;
    mapping(address => uint48) sessionExpiries;
}

function _getStorage() private pure returns (WalletStorage storage $) {
    assembly {
        $.slot := STORAGE_LOCATION
    }
}

3. 致命陷阱二：chain_id = 0 全链重放与 initialize() 同块抢跑

除了存储污染，EIP-7702 签名元组自身的灵活性也引入了两条高频攻击路径：

1）chain_id = 0 跨链通配重放与非确定性地址劫持

按照规范，当授权元组的 chain_id 填为 0 时，该签名在所有支持 EIP-7702 的 EVM 网络上均有效。一旦你在以太坊主网或某条 L2 广播了这笔交易，签名数据即全网公开。攻击者可以立刻提取该元组，在 Arbitrum、Base、Optimism 等任何该 EOA 尚未用掉对应 nonce 的链上进行重放。更致命的是，如果目标实现合约 address 在主网上是用传统 CREATE（依赖部署者地址与 nonce）部署的，而在另一条链上该地址尚未被项目方占领，攻击者完全可以通过同源 nonce 或碰撞手法在目标链的相同地址部署恶意合约，再重放你的 chain_id = 0 授权，瞬间接管你在该链的全部资产。

2）无鉴权 initialize() 的同块抢跑接管

由于 EIP-7702 允许任意第三方（如代付 Gas 的 Sponsor）替用户提交 authorization_list，很多从传统代理模式迁移过来的合约保留了公开的 initialize(address owner) 函数。攻击者只需在内存池（Mempool）监听到用户的 0x04 交易，剥离其中的授权元组并打包进自己的高优先费交易，在设置完委托代码的同一笔交易里抢先调用 eoa.initialize(attacker)，就能反客为主锁定受害者 EOA 的代理管理权。因此，任何面向 EIP-7702 的初始化函数，要么严格限制 require(msg.sender == address(this))（只能通过 EOA 自身批量调用触发），要么在初始化载荷中强制校验 EOA 本人的 ECDSA 签名。

4. 致命陷阱三：tx.origin == msg.sender 防线全面崩塌

在 EIP-7702 之前，大量老牌 DeFi 协议、NFT 铸造合约与链上抽奖/空投合约普遍采用以下两行代码来“禁止合约调用、仅限真实用户 EOA 参与”：

// EIP-7702 激活后，以下两类“防合约/防闪电贷”校验全部失效
require(msg.sender == tx.origin, "Only EOA allowed");
require(msg.sender.code.length == 0, "Contract caller forbidden");

在 EIP-7702 下，这两条假设被同时击穿：当一个已经设置委托代码的 EOA 自己发起交易时，在下游 DeFi 协议的调用栈中，tx.origin 是该 EOA，msg.sender 同样是该 EOA——msg.sender == tx.origin 恒为 true！然而，该 EOA 在这笔交易内部已经通过委托代码执行了包含闪电贷借入、多池套利、循环铸造与还款在内的完整合约逻辑。与此同时，对普通用户而言，如果某个旧协议依然使用 msg.sender.code.length == 0 拒绝带代码地址，则升级为 EIP-7702 的合规钱包反而会被意外拒之门外（因为此时 extcodesize 返回 23 字节而非 0）。研究者在评估 DeFi 协议抗闪电贷与抗女巫模型时，必须彻底剔除基于 tx.origin 的安全假设，转向基于区块延迟（Commit-Reveal）或状态不变量（Invariant）的真实防线。

5. 可执行链上核验规程：RPC 探测与安全自查命令

无论是普通研究员排查自身 EOA 状态，还是安全团队审计拟接入的 EIP-7702 钱包实现，都可以直接通过 Foundry cast 或标准 JSON-RPC 执行以下四步硬核核验：

# 1. 检查目标 EOA 当前是否处于 EIP-7702 委托状态（正常委托必返回 23 字节且前缀为 0xef0100）
cast code 0xYourEOAAddress --rpc-url $RPC_URL
# 若返回 0xef0100<20-byte-impl>，提取后 40 位十六进制即为当前实现合约地址；返回 0x 则无委托

# 2. 撤销委托后，抽查线性低位槽位 0..3 是否仍残留历史脏数据
cast storage 0xYourEOAAddress 0 --rpc-url $RPC_URL
cast storage 0xYourEOAAddress 1 --rpc-url $RPC_URL

# 3. 核验目标实现合约在多条链上的字节码哈希是否完全一致（防范非确定性部署劫持）
cast codehash 0xTargetImplAddress --rpc-url $ETH_MAINNET_RPC
cast codehash 0xTargetImplAddress --rpc-url $ARB_ONE_RPC

结合上述实测结果，建立上线前与签署前的刚性准入门槛：

  1. 拒绝盲签 chain_id = 0：钱包弹窗若未明确展示当前目标链 ID，或签名原文中 chain_id 为 0，一律中止签署；
  2. 源码必查 ERC-7201 与 onlySelf：在区块浏览器核对 0xef0100 指向的实现合约源码，确认无裸露线性状态变量，且所有初始化/升级入口均校验 msg.sender == address(this) 或 EOA 签名；
  3. 切换委托先清槽再换绑：若旧版实现合约未采用 ERC-7201 且提供清理函数，应在撤销前主动归零关键槽位，并保留 eth_getStorageAt 核验快照作为链上留证。

推广信息：在跨以太坊主网与各条 Layer 2 实测 EIP-7702 委托状态、比对不同链的 codehash 与合约部署一致性时，研究者往往需要在多条公链准备小额 Gas 与测试资产。若在链上协议研究之余需要进行便捷的多链资产调仓或跨链兑换，可参考体验 Allswap 跨链兑换。该工具仅供跨链资产调度与实测参考，与 EIP-7702 底层协议核验无关，不构成任何投资建议；链上交互前请务必核对目标网络、收款地址与合约授权权限。
